# GameCube symbol sets: where to find which versions

A lookup table of 319 GameCube development symbol sets (link maps, ELF files with and without DWARF, executables and relocatable modules), so you can find the sets that match your game's Dolphin SDK build and middleware, and that hold the data you need. Made with `targets/gamecube_ppc/tools/symbol_inventory.py` on 2026-11-14.

**What this is made from.** Only facts read from the contents of the files: SDK build strings, compiler and MetroTRK strings, library and object names, symbol counts, section names. Nothing is taken from file names except the set's own name, game ID, region, version and any date written in that name. A field that could not be read says "not known". **It contains no symbol files, no name lists and no game code**, and it makes no claim about where a set came from.

**The numbers.** 319 sets. SDK build strings read in 223 of them; 90 more carry only the "Dolphin OS $Revision" string of an older SDK; 79 sets have text or binary map files; 308 have function names (from a map or an ELF symbol table); 304 have function names together with the code they name (an ELF, or a map with a matching .dol/.elf/.rel); 124 have DWARF. Every one of the 223 sets with SDK strings reports the SDK code `0x2301`, so the code does not separate builds: **the library build dates do**.

Also published, one row per set with the same fields: `GAMECUBE_SYMBOL_SETS.csv` and `GAMECUBE_SYMBOL_SETS.json` (stable field names; the JSON also holds every SDK library's build date and the middleware evidence).

## How to use it

1. Read your game's SDK build from its `main.dol` (next section). Note the OS library's build date, e.g. `Nov 26 2003 05:18:37 (0x2301)`.
2. Find that date in "By SDK build" at the end. Sets on the same OS build date link the same SDK code. Then look at the nearest dates on either side.
3. In the table, check what each set can give: **Fn names** (function names), **Sizes**, **Bytes** (the set also holds the code, so names can be matched to another game by bytes), **Lib/obj** (which library and object each function came from), **SDK fns**, **MSL**, **TRK**, **Data**, **DWARF**. Prefer a set with function names, sizes and library attribution on your build date.
4. For middleware (MusyX, JSystem, Bink and so on), use the middleware index at the end.
5. The set's folder name is in the **Set** column exactly as it is named. **Copies** counts sets with an identical file list (same relative names and sizes).

## Reading your own game's SDK build (no tool needed)

The Dolphin SDK libraries stamp their build into the executable as text. Search your `main.dol` (or any `.elf`/`.rel`) for the string `<< Dolphin SDK - `, with any hex editor, `strings` or a script. Each line is one library:

```
<< Dolphin SDK - OS<TAB>release build: Nov 26 2003 05:18:37 (0x2301) >>
```

- The library comes first (OS, DVD, VI, PAD, AI, AR, ARQ, DSP, CARD, GX, EXI, SI; some games add ETH, IP, HIO, AX, THP, GBA and others). Then `release` or `debug`, the date and time that library was built, and the SDK code in parentheses.
- Libraries are built at different times, so the dates differ within one game. The OS library's date is the best single key; the full list is the real fingerprint.
- Older SDKs (about 2001 to early 2002) have no such lines. They carry `Dolphin OS $Revision: 54 $.` instead (look for `Dolphin OS $Revision`). The table lists these as "OS revision N only".
- Some games embed none of this. Then the table has no SDK build for sets like yours and the middleware index is the way in.

## Example

Your `main.dol` says `OS ... release build: Sep 5 2002 05:32:39 (0x2301)` and `DVD ... Sep 5 2002 ...`.
- **Same build:** "By SDK build" lists the 8 sets whose OS library has that date. Those whose **Fn names** come from an ELF symbol table also hold the code (**Bytes** `elf`) and name SDK functions with sizes, but give object names, not libraries.
- **Nearest builds either side:** `Sep 27 2002 14:02:03` and `Nov 5 2002 12:52:29` have sets whose maps name the library and object of every function (**Lib/obj** `lib+obj`). Check them next.
- **Middleware:** if your game uses MusyX or JSystem, the middleware index lists the sets that link them.

## Columns and legend

- **Set**, **Copies**, **Has** (file types in the set, with a count when there is more than one), **Game ID** (from the name).
- **SDK build:** the SDK code, `release`/`debug` as stamped, the range of library build dates, and how many libraries were read. "OS revision N only" is the older string. Per-library dates are in the JSON.
- **Compiler:** the first compiler string found in the executables (CodeWarrior builds do not state a version string in these files; "not known" where none was read). **Cfg:** `release`/`debug` as stamped in the SDK strings, plus Debug/Release/Final/Profile/Master where such a word is a path component in the set.
- **Fn names** `yes N`: N distinct function names across all maps of the set, or the ELF symbol table if it holds more. **Sizes:** yes when sizes are nonzero in the map columns or the ELF symbols.
- **Bytes:** `dol/elf` the map's addresses fall inside a .dol/.elf of the same set; `elf` the ELF holds its symbols and code; `rel` map addresses are module-relative and the set holds .rel modules; `no` nothing in the set to match against.
- **Lib/obj:** `lib+obj` the map says which `.a` and which object; `obj` object or source-file names only; `no`.
- **SDK fns** `yes N`: functions attributed to the Dolphin SDK libraries (os, dvd, vi, pad, ai, ar, dsp, card, gx, exi, si, mtx, base, db and so on). A `*` marks a count made by function-name prefix (OS*, GX*, DVD*, ...) because the set has no library column. **MSL:** C/C++ runtime (MSL, Runtime) functions named. **TRK:** MetroTRK functions named. **Data:** data symbols named.
- **DWARF:** sections found in an ELF (`.debug`/`.line` is DWARF 1 as CodeWarrior writes it; `.debug_info`/`.debug_line` is DWARF 2). Only presence is recorded, not content.
- **.rel maps:** relocatable modules that have a map of their own, "n of m".
- A map that exists but holds no readable function lines reads "no": binary `SYM1` maps, encrypted or non-text maps and file tables are listed as such in the JSON (`map_kinds`).
- **Middleware:** found by library and object names, or by strings in the executables, with a version where a version string was read. Library names alone need two distinct matches; one name does not count.
