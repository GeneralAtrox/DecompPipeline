# TC 8c0923e0 (Lib_ScreenReadPixel): proven through a modelled video memory read (tcdone, 2026-10-30)

Nearest existing: `docs/proofs/tcdone/8c0580b8.md` (same note shape for one function); the oracle model itself is the
`hw_ops` "read area5" precedent extended by one op, "read vram" (core/hw_ops.py, TcHw.java, TcBase.vramWord).

## What the function does
It reads one pixel of the frame buffer: a 16-bit load from `0xa5000000 | (base + 2 * index)`, an address in the PVR
video memory window (0xa5000000..0xa57fffff), then expands the RGB565 pixel to four floats. The earlier round skipped it
because the oracle had no model of that window ("unsupported: hardware register a5000000 ... not listed").

## The model (all three runners give the same word)
The window's content is a fixed function of the address: `((A >> 2) & 0x1fffff) * 0x9e3779b1 + 0x7f4a7c15`.
- oracle: `TcBase.vramWord` (Ghidra emulator) - the word the load returns;
- raw runner: `tcrt_vram_word`; readable runner: `rd_veh.c` reserves the whole window once and commits the pages read-only;
- the function is listed in project.json `hw_ops["8c0923e0"] = {"ops": ["read vram"], "evidence": ...}`; `hw_ops.covered`
  counts the op as the register `0xa5000000`, so `prepare` no longer refuses the function;
- hints (`oracle/hints/8c0923e0.txt`) keep the buffer words and the index small and even so the address lands in the window,
  as the game's frame buffer offsets do.
Changing the oracle scripts changed every harness stamp; `selective_restamp --change zeroread` sampled 20 functions
(identical), then refreshed 2710 stamps. Nothing was re-prepared for it.

## The two survivors
- m04 `>> -> <<` in `(0x18u) == 0 ? ... : (u32)((s32)r4 >> 31)`: the mutated arm sits under a constant condition that is
  false (`0x18 != 0`), so it never runs: an equivalent mutant.
- m09 `return v.f -> return 0` in `u2f`: u2f turns the callee's result into `fr0`, which the original hands on in fr0 to
  the call to 8c09ac00. The judge's callee record does not compare fr0 as an argument of that call (the callee's
  storage names no fr0 parameter), so a wrong fr0 there is not seen. This is a limit of the callee record, recorded
  here, not a weakened check. What would remove it: the record carrying fr0 for a callee whose own harness reads it
  (a judge change that needs its own 0-lost-kill proof).

Nothing in the judge was weakened for this function: no vector was dropped, no verdict edited.
